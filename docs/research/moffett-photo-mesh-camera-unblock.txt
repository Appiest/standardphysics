The previous diagnosis was partly wrong
Let F=diag(1,-1,-1,1), C=capture_to_room and T=ARKit camera-to-world.
camera.py produces W=F @ inv(T) @ inv(C), therefore inv(W) @ F = C @ T.
Across the saved 12 cameras the two expressions agree within 4.44e-16.
The alleged 165-177-degree mismatch compares unlike coordinate conventions.
The extra A_yup belongs to a camera expressed in GLTF coordinates. Blender's
default GLTF importer already restores our exported (x,z,-y) geometry to the
original room frame. Applying A_yup again to this Blender camera is incorrect.

The demonstrated error was omitted principal-point calibration. The old Stage B
renderer sets focal length and pose but leaves camera shifts at zero. For
frame-0088 its centring predicts (-1.226,-1.860)px candidate-minus-source at 500px,
close to the reported (-1.29,-1.84)px shift. Unequal fx/fy is also now supported.
For horizontal sensor fit, using the cropped/resized PhotoCamera parameters:
  matrix_world = inv(room_to_camera) @ F
  lens_mm = fx * 36 / width
  aspect_y / aspect_x = fx / fy
  shift_x = (width/2 - (cx + 0.5)) / width
  shift_y = ((cy + 0.5) - height/2) * (fx/fy) / width
Blender view-layer updates precede projection checks. These equations are for
Blender's default imported world, not arbitrary unconverted Y-up scene geometry.

The old synthetic fixture was itself invalid: it inserted rotation rows into
camera-to-world and flipped only Z, producing det=-1. That test did not establish
a Blender rendering fault. The new fixture uses oblique/translated cameras,
unequal focal lengths, an off-centre principal point, actual GLTF import and
five colored markers at independently derived pixel locations plus an untextured
marker. It checks rendered centroids, positive rotation determinant and masks.
