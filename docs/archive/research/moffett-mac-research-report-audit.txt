New backend finding: msplat

The delegated source audit verifies https://github.com/rayanht/msplat is a real
Apache-2.0 Apple GPU trainer: C++/ObjC++ core, Metal forward/backward rasterization,
SSIM, Adam and densification, plus CLI/Python/Swift interfaces. This is a credible
candidate for a baseline benchmark; it was not compiled or run in this audit.

The report misquotes its speed by mixing iteration counts. Upstream README
reports 59–80 seconds for 7,000 iterations on M4 Max. Its 30,000-iteration garden
run reports 700 seconds and 3.51 million Gaussians, not 70 seconds. These are author
benchmarks, not our Moffett timings or an equivalent-quality comparison to Brush.
The README's approximately 2 GB reference concerns PyTorch framework overhead,
not a measured 2–4 GB msplat training footprint.
Source: https://github.com/rayanht/msplat/blob/main/README.md#L162-L190
Source: https://github.com/rayanht/msplat/blob/main/core/metal/msplat_metal.mm
Source: https://github.com/rayanht/msplat/blob/main/core/metal/msplat_metal.metal

Upstream Swift/build configuration targets macOS. A real iOS fork exists at
https://github.com/frs0n/msplat-ios, with iOS 18 build support. Its README explicitly
says upstream benchmarks have not been rerun. The example memory log reports
phys=2908.4MB at 232,313 splats with a 2048 MB image budget. This does not verify
the report's 700k splats / under-three-minutes / 2 GB total claim.
Source: https://github.com/frs0n/msplat-ios/blob/main/README.md#L98-L111

Recommendation update: benchmark unmodified msplat on the controlled patch before
choosing a backend for new geometry losses. Verify per-frame camera calibration,
coordinate conventions and mask behavior first. Do not substitute unmasked inputs
and then attribute any difference solely to the backend. No speed promise follows
from the published M4 Max results for this M5 Pro capture workload.

Implementation corrections

- A flattened initialization does not constrain later optimization. Bounds must
  be enforced in the optimizer/parameterization and preserved across refinement.
- Rotation from +Z via normalized cross product is undefined for normals +Z/-Z.
  Handle parallel/antiparallel and invalid normals explicitly; test export axes.
- Scale along a fixed axis is normal thickness only while that axis stays aligned
  to the surface. Handle anchor-frame rotation and displacement consistently.
- The proposed sum(T*alpha*z) is accumulated depth, not conditional expected
  surface depth unless opacity is accounted for. Define depth convention and
  background, coverage thresholds, mesh validity, and uncertainty before loss.
- Depth supervision needs forward output, derivatives through compositing,
  backward integration and gradient checks. It is not just adding a scalar loss
  kernel. Start with parameter constraints before undertaking a rasterizer port.
- Do not fix depth weight to 0.5 without checking units and gradient magnitudes.
- LiDAR holes/noisy normals require exclusions. Constraints cannot reconstruct
  unseen photographic detail or establish centimetre accuracy/ADA compliance.
- vm_stat reports system memory; it is not a process peak-memory measurement.
  Record process footprint and GPU allocations with documented measurement scope.
